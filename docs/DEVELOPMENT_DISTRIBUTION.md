# Sviluppo e distribuzione — 0.7.3

1. I sorgenti del motore restano nella cartella 2Dog (`src`, `include`, `managed`, `scripts`, `cmake`). La cartella `build` contiene risultati rigenerabili. Conserva i progetti personali fuori da queste cartelle.
2. Il progetto del gioco contiene `project.json`, asset, scene e script originali. Le cartelle dei tuoi script vengono mantenute nella soluzione Visual Studio mediante collegamenti ai file originali: salvare nell’IDE modifica proprio questi file.
3. `ProjectLayout` centralizza i percorsi di sviluppo. Nel progetto, `.twodog/cache/ide` contiene gli intermedi della soluzione; `.twodog/cache/scripts` contiene progetto e build runtime; `.twodog/cache/exports` contiene i lavori temporanei dell’export. I log sono in `.twodog/logs`, le impostazioni export in `.twodog/settings/export.json`.
4. `.twodog/GameScripts.sln` è la soluzione da aprire nell’IDE. Comprende GameScripts e TwoDog.API, con copie aggiornate delle API in `.twodog/EngineAPI/Sources`. Queste copie permettono navigazione e completamento, ma non sono il posto in cui modificare il motore. Modifica le API originali in `managed/TwoDog.API`, ricompila il motore e aggiorna il progetto IDE.
5. La soluzione di sviluppo usa SDK .NET 8 e C# 12 per compatibilità con Visual Studio 2022. Play ed export usano SDK .NET 10, C# 12 e la DLL TwoDog.API effettivamente distribuita. I rispettivi `global.json` e intermedi sono separati. Installare entrambi gli SDK x64; l’SDK 10 da solo non sostituisce l’SDK 8 per questa soluzione.
6. Questo profilo supporta tutte le API 2Dog attuali; non espone nell’IDE le API del framework disponibili soltanto in .NET 9/10 e non abilita sintassi successiva a C# 12. Per usare quelle funzionalità servirà un profilo IDE aggiornato, non incluso qui. Riferimento Microsoft: https://learn.microsoft.com/en-us/dotnet/core/porting/versioning-sdk-msbuild-vs
7. `Refresh IDE project` nel pannello Assets rigenera i riferimenti e aggiorna i sorgenti delle API. L’apertura di uno script verifica l’SDK e ripristina i riferimenti prima di aprire Visual Studio. Errori e dettagli sono in `.twodog/logs/ide.log`. Il log della compilazione runtime è `.twodog/logs/compile.log`.
8. `WindowsExport.cpp` contiene soltanto interfaccia, scelta cartelle, salvataggio della scena tramite callback e visualizzazione. `ExportService`, nel target TwoDogDevelopmentTools privo di ImGui, gestisce impostazioni, avvio del processo e lettura dello stato/log. `export-windows.ps1` prepara e pubblica il pacchetto, usabile anche senza editor.
9. La build Windows produce il target TwoDogRuntimeTemplate in `build/export-templates/windows-x64/<config>`. Contiene solo gli ingressi necessari all’export: player, host e API, nethost, script demo, licenze e metadati. Il pannello e lo script preferiscono il template Release. Non è ancora il gioco distribuibile.
10. Il gioco esportato viene creato nella destinazione scelta, fuori dal progetto e dai sorgenti dell’engine. Include asset selezionati con dipendenze, player, script compilati, runtime .NET e licenze. Non include l’editor, Hub, soluzione IDE, sorgenti C# o cache di sviluppo. Il manifesto contiene gli hash del pacchetto. La pubblicazione conserva una build esistente se la nuova compilazione fallisce.
11. I progetti esistenti vengono aggiornati quando vengono riaperti nell’editor. Le vecchie impostazioni `.twodog/export-settings.json` sono lette come fallback; il successivo salvataggio usa il nuovo percorso. Se il campo Runtime punta ancora a `build/bin/Release`, seleziona il nuovo template Release dopo la ricompilazione.
12. Non viene eseguita alcuna cancellazione automatica dei vecchi dati. Per liberare spazio chiudi IDE/editor e rimuovi soltanto cache e log identificati: non cancellare alla cieca l’intera `.twodog`, perché può contenere impostazioni o vecchi script Builtin personalizzati. Gli asset originali non devono mai essere eliminati durante una pulizia della build.
